## 背景
第二阶段必须建立在第一版静态站已经稳定上线并被客户接受的前提下。当前重点不是建设通用后台基础设施，而是给非技术客户提供足够简单的内容编辑能力。

## 目标 / 非目标
- 目标：
  - 让客户无需改代码即可更新首页主视觉和产品内容。
  - 提供足够直观、低维护成本的编辑界面。
  - 保持前端页面结构不变，只替换内容来源。
- 非目标：
  - 不自研账号系统。
  - 不支持任意页面自由搭建。
  - 不引入超出当前业务体量的重型后端维护成本。

## 关键决策
- 决策：第二阶段使用 Sanity 作为 CMS。
  - 原因：Sanity 自带成熟的内容编辑界面、媒体管理、结构化 Schema 和用户权限，更贴合当前需求。
- 决策：CMS 范围先限制在首页与产品内容。
  - 原因：这是客户当前真正需要的范围，也最容易稳定交付。
- 决策：前端区块组件保持不变，只替换数据获取方式。
  - 原因：保护第一版已经打磨好的视觉表现，减少接入 CMS 的回归风险。

## 备选方案对比
- Supabase：更像后端基础设施，若要达到友好的内容编辑体验，仍需额外开发后台页面。
- 自研后台：开发时间长、维护成本高，不适合当前项目规模。
- 迁移到 WordPress：可以实现编辑，但会增加主题和系统复杂度，也可能削弱当前前端视觉一致性。

## 风险与权衡
- 风险：CMS Schema 与第一版本地数据结构不一致。
  - 应对：在第一版阶段就让本地数据尽量贴近 CMS 结构。
- 风险：客户不熟悉发布流程。
  - 应对：控制 Schema 复杂度，并提供极简交接说明。

## 迁移计划
1. 创建 Sanity Workspace 与内容 Schema。
2. 将第一版站点内容作为初始数据录入或导入。
3. 在前端接入 Sanity 查询。
4. 验证内容修改后可正确反映到线上页面。
5. 完成客户培训与交接。
